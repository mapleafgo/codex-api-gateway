# Feature Specification: 图片识别三协议完全可用

**Feature Branch**: `011-image-recognition-complete`

**Created**: 2026-08-31

**Status**: Draft

**Input**: User description: "当前多模态部分，我们转换还没做，我们补充下。先做图片识别和生成；图片识别要做到三协议（Anthropic / Chat / Responses）完全可用。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 识别图片在三协议完整到达上游 (Priority: P1)

用户向网关发送一条包含图片的对话请求，图片以 URL 或内嵌数据地址出现在用户消息或
工具结果等目标协议允许承载视觉内容的合法位置。网关必须把图片转换成所选上游契约的
原生视觉内容槽位，并尽可能保留图片的展示控制信息；不能把图片替换成普通文本占位，
也不能让模型只看到“有一张图”却看不到图本身。

**Why this priority**: 图片识别是多模态会话的基础能力；识别输入丢失或降级会让用户
可见输入失真，并直接导致模型答非所问。

**Independent Test**: 分别用 URL 图片和内嵌数据图片、带与不带 detail 档位发起请求，
检查 Anthropic / Chat 两类后端收到的请求包含等价图片内容，Responses 透传源保持原样，
且客户端能收到基于该图片的正常回答。

**Acceptance Scenarios**:

1. **Given** 用户消息含 URL 图片和文本，**When** 请求命中 Anthropic 或 Chat 源，
   **Then** 上游收到与该图片等价的原生内容项，文本顺序保持可理解，客户端收到正常
   SSE 响应。
2. **Given** 用户消息含内嵌数据图片，**When** 请求命中任一已配置源，**Then** 上游
   收到同一图像数据，网关不要求外部文件服务可达。
3. **Given** 工具结果内容数组中包含图片，**When** 该结果需要回灌到上游，**Then**
   上游在协议允许的位置看到该图片；相邻文本和调用关联关系保持可用。
4. **Given** 用户图片携带 detail 档位（low / high / auto / original），**When**
   目标协议存在等价 detail 槽位，**Then** detail 被保留透传；目标协议无等价槽位时
   **Then** detail 被有损丢弃但图像本体完整到达上游。

---

### User Story 2 - 无法无损映射时明确失败并换源 (Priority: P2)

用户请求中的图片无法无损承载到某个非透传上游（例如只给文件编号的识别图片、出现在
系统或开发者指令中的图片）。网关必须在调用该上游前明确判定该源不可映射并进入既有
换源流程，而不是悄悄丢弃图片后把残缺请求发给上游，避免误导模型产出答非所问结果。

**Why this priority**: 有损丢弃会制造“模型没看到图却以为看到了”的假象；明确失败
才能让换源和错误终态可预期。

**Independent Test**: 用只含文件编号图片的请求配置多个源，验证每个非透传源在调用
上游前失败、整轮按既有规则换源，全部候选不可用时客户端收到确定性转换错误；再验证
系统或开发者指令含图片时行为一致。

**Acceptance Scenarios**:

1. **Given** 识别图片只有文件编号（file_id），**When** 目标是非透传源，**Then**
   网关在调用该上游前产生源级协议映射失败；若存在兼容源则按既有调度规则继续尝试，
   客户端最终获得成功结果或整轮确定性错误。
2. **Given** 识别图片只有文件编号，**When** 目标是 Responses 透传源，**Then**
   该引用被原样保留交由上游解析，网关不代拉取、不丢弃。
3. **Given** 系统或开发者指令包含图片，**When** 目标是 Anthropic 或 Chat 源，
   **Then** 该源按协议不可映射失败并允许既有换源流程继续，网关不得把图片丢弃后把
   残缺指令发给该上游。
4. **Given** 系统或开发者指令包含图片，**When** 目标是 Responses 透传源，**Then**
   图片随指令原样透传，由上游决定是否支持。

---

### User Story 3 - 图片相关观测不泄露且可归因 (Priority: P3)

运维人员排查图片相关请求时，日志和观测必须能归因到路径与原因，但不得泄露凭据、完整
图片地址参数或大体积图像数据。图片 URL 只记录基础地址，内嵌数据图片只记录类型与
大小等元数据。

**Why this priority**: 图片地址常携带签名或令牌；观测泄露会扩大凭据暴露面，而完整
记录大体积数据会污染日志。

**Independent Test**: 发起带签名参数的图片 URL 与内嵌数据图片请求，检查日志断言不
含查询参数、片段与数据本体；含文件编号图片的失败样例能定位到路径与原因。

**Acceptance Scenarios**:

1. **Given** 图片 URL 携带签名或令牌查询参数，**When** 该地址进入日志，**Then**
   只记录协议、主机、路径等基础地址，查询参数与片段不进入日志。
2. **Given** 请求包含内嵌数据图片，**When** 该图片进入日志，**Then** 只记录类型与
   大小等元数据，不记录完整数据本体。
3. **Given** 图片相关错误或跳过发生，**When** 观测该事件，**Then** 错误可归因到
   路径与原因，且不含 Authorization、API key 等凭据。

### Edge Cases

- 同一请求混有多张图片、多种引用方式：每张图片独立判断可映射性；任一图片在某个
  非透传源不可映射时，该源不得发送丢失内容的残缺请求，而应作为源级失败进入既有
  换源流程。
- 图片既有 URL 又有文件编号：URL 优先映射，文件编号不作为失败依据。
- 图片没有 URL 也没有文件编号（畸形）：按协议不可映射处理，非透传源源级失败，
  透传源交由上游决定。
- detail 为 original：Responses 原生支持；Anthropic 无等价槽位按 lossy 丢弃登记；
  Chat 按对应 detail 槽位透传。
- 系统或开发者指令图片与普通文本混排：该源按不可映射失败，不得把文本剥出后丢弃
  图片继续发送。
- 上游返回拒绝、空答案或格式限制：由上游表现，网关不代为判定“该模型一定不支持
  图片”，也不把失败包装成成功。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 将用户消息和工具结果中的图片识别输入（URL 与内嵌数据）映射
  到所选非透传目标协议的原生视觉内容槽位，图像本体 MUST 保持可用。
- **FR-002**: 图片识别输入的展示控制字段（detail），在目标协议存在等价槽位时 MUST
  保留透传；无等价槽位时 MAY 有损丢弃，但系统 MUST 在协议覆盖矩阵登记损失，且 MUST
  NOT 因 detail 无法映射而丢弃图像本体。
- **FR-003**: 仅包含外部平台文件引用（file_id）的识别输入，在非透传源 MUST 触发
  明确的源级协议不可映射失败并进入既有换源流程，MUST NOT 静默替换为文本占位；
  Responses 透传源 MUST 原样保留该引用。
- **FR-004**: 系统或开发者指令中的图片，在目标协议无图片槽位时 MUST 触发该源的
  协议不可映射失败，调度器 MUST 按既有规则尝试后续可用源；系统 MUST NOT 只丢弃
  图片后把残缺指令发给该上游。
- **FR-005**: 图片相关失败 MUST 使用既有 error 或 SSE 错误终态语义，MUST NOT 为
  图片场景引入成功假象、静默断流或绕过调度锁定规则。
- **FR-006**: 图片 URL 进入日志前 MUST 抹掉查询参数和片段、只保留基础地址；内嵌
  数据图片 MUST 只记录类型和大小等元数据；日志与观测 MUST NOT 记录凭据或完整
  大体积图像数据。
- **FR-007**: 图片识别、detail 档位、file_id 与系统指令图片在每条上游类型 MUST
  于协议覆盖矩阵分别登记，禁止跨路径复用状态；矩阵状态 MUST 与实现和验收样例一致。

### Key Entities

- **图片识别输入**: 用户或工具结果带给模型的视觉证据；关键属性包括图像本体或外部
  引用、所在消息角色、展示控制（detail）和与其他内容的顺序。
- **映射判定**: 对每条图片输入做的可映射性判定；关键属性包括引用形态（URL / data
  URI / file_id）、目标协议槽位可用性与展示控制字段的等价槽位。
- **上游契约类别**: 决定同一图片数据走语义映射还是最小透传；不同类别的覆盖状态
  必须独立维护。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 对两类受支持的图片识别样例（URL、内嵌数据），100% 的合法请求能在
  Anthropic 与 Chat 上游请求中找到等价图像内容，Responses 透传源保持原样，客户端
  回答与图像相关。
- **SC-002**: detail 档位在 Chat 与 Responses 路径 100% 保留透传；Anthropic 路径
  100% 有损丢弃并完成矩阵登记，图像本体不因 detail 丢失。
- **SC-003**: 仅 file_id 的识别输入在非透传源 100% 在调用该上游前产生源级协议
  映射失败；存在兼容源时请求可成功，全部候选源不可用时客户端 100% 收到确定性
  协议映射错误。
- **SC-004**: 系统或开发者指令含图片的请求在 Anthropic / Chat 源 100% 产生源级
  映射失败，且不会向该上游发送丢失图片后的残缺指令；Responses 透传源 100% 原样
  保留。
- **SC-005**: 图片相关错误、跳过和终态在观测中可归因到路径与原因；凭据和大体积
  图像数据泄露次数为 0。
- **SC-006**: 协议矩阵对图片识别、detail、file_id 与系统指令图片在三路径上的状态
  描述与实现和验收样例完全一致。

## Assumptions

- 本特性补齐图片识别在三条上游路径的协议处理，不新增图像生成模型、文件存储、
  图片代理或本地 session store。
- 图片生成（透传验证、非透传源历史回灌等）不纳入本次范围，作为后续独立特性处理。
- 上游是否真正支持某个模型或图片选项，始终由上游运行时决定；网关只区分“协议是否
  有安全槽位”。
- 外部平台文件引用不在网关侧取回或缓存；能否解析取决于所选上游。
- 依据官方协议：Anthropic 的 system 参数只接受文本、Chat 的 system 消息协议不支持
  图片内容，因此系统或开发者指令图片在这两个非透传源属于协议不可映射；Responses
  原生允许 system/developer 携带图片，由上游裁决。
