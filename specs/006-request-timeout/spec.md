# Feature Specification: 单请求最大超时时长配置

**Feature Branch**: `006-request-timeout`

**Created**: 2026-08-20

**Status**: Draft

**Input**: User description: "我们给加一个配置项，配置单请求最大超时时长，默认120s。现在有些源跑了360s,结果没有任何数据"

**用户澄清**: 超时作用于单个源的单笔请求，不是客户端请求的整轮。

## Clarifications

### Session 2026-08-20

- Q: 单笔请求总时长是否允许按源单独覆盖，还是 v1 只做全局单一配置？ → A: 全局默认 + 可选每源覆盖（沿用 `first_byte_timeout` 的覆盖模式）。
- Q: 单笔请求已向客户端发出内容后到达总时长时，以哪种事件形态收尾？ → A: failed 错误终态（保留已收内容，随后收到明确超时错误终态）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 单笔源请求超时兜底，杜绝单源无限挂起 (Priority: P1)

网关处理一个客户端请求时，每一个发起的上游源调用（单笔请求）都受配置的最大
时长约束：某源的单笔请求到点时即被终止并按失败处理，网关随后按既有顺序继续
尝试其他可用源。单个源挂起 360 秒却没有任何数据成为不可能。

**Why this priority**: 这是本次需求的核心目标，直接消除用户观察到的"单源跑了
360 秒没有数据"问题。

**Independent Test**: 配置一个短超时（如 3 秒），用一个迟迟不输出数据（或只
发出状态事件后静默）的上游作为首个源发起请求，验证该源在接近 3 秒时被终止并
按失败处理，网关继续按既有顺序尝试备用源，客户端最终收到合法终态。

**Acceptance Scenarios**:

1. **Given** 未配置该选项，**When** 发起任意请求，**Then** 每笔源请求默认按
   120 秒执行。
2. **Given** 配置为 3 秒且首源迟迟不产生数据，**When** 发起请求，**Then**
   首源在约 3 秒时被终止并按失败处理，请求继续按既有顺序尝试备用源。
3. **Given** 所有源的单笔请求均超时，**When** 一轮耗尽，**Then** 客户端收到
   错误终态，不再无限挂起。
4. **Given** 某源配置了覆盖值（如 60 秒）而全局为 120 秒，**When** 请求命中
   该源，**Then** 该源按覆盖值计时，其余源按全局值计时。

---

### User Story 2 - 超时与客户端取消可区分 (Priority: P2)

单笔源请求超时导致的结束与客户端主动取消造成的结束，必须能在终态、日志与指标
中明确区分：超时归因于网关侧终止，取消归因于客户端，不能互相混淆。

**Why this priority**: 可观测性与排障事实链要求，超时与取消是两类不同根因，
混淆会掩盖上游挂起问题。

**Independent Test**: 分别触发一次单笔源请求超时和一次客户端取消，检查两者的
终态、日志与指标原因互不相同，且与各自场景对应。

**Acceptance Scenarios**:

1. **Given** 网关侧单笔源请求超时到点，**When** 该笔请求结束，**Then** 终态与
   日志标记为超时原因，而不是 canceled。
2. **Given** 客户端主动断开，**When** 请求按既有取消语义结束，**Then** 该
   结束不被误判或改写为超时。

---

### User Story 3 - 已出流的单笔请求同样被兜底 (Priority: P3)

即使某源已开始出流（例如先发出状态事件，之后长时间没有实质内容或终态），该笔
请求的总时长到点同样终止；客户端收到已发生的事件与收尾终态；该笔请求已锁定
源时不再换源。

**Why this priority**: 现状下"已出流"会让首字节超时提前失效，这正是观察到的
单源 360 秒无数据挂起的直接成因，属于本次需求必须覆盖的路径。

**Independent Test**: 用先发出一个非内容事件、随后静默的上游发起请求，验证该
笔请求总时长到点即被终止；再调大配置值重复一次，验证终止边界随新值平移。

**Acceptance Scenarios**:

1. **Given** 某源单笔请求已发出事件但长时间无实质内容或终态，**When** 该笔总
   时长到点，**Then** 该笔请求被终止，客户端保留已收内容并收到 failed 错误
   终态，源保持锁定不换源。
2. **Given** 配置值被调大，**When** 长任务仍在持续出流，**Then** 在达到新配置
   值之前请求不提前中断，行为边界随配置值平移。

### Edge Cases

- 单笔超时发生在任何事件写出之前：该源按既有失败逻辑计入熔断统计，网关继续按
  既有顺序尝试其他源；若该源已是最后一源或已锁定，按锁定/整轮收口语义结束。
- 单笔超时发生在已有事件写出之后：源保持锁定，客户端保留已收到的事件并收到
  failed 错误终态，不换源。
- 某源显式配置了覆盖值时：该源按覆盖值执行，其余源按全局值执行；覆盖值同样
  遵循负值拒绝、为 0 走默认的校验规则。
- 退避等待与整轮重试的等待间隙不属于任何单笔源请求，不受该配置直接约束，按
  既有逻辑执行。
- 客户端取消早于超时到点：按既有 canceled 语义处理，不被覆盖为超时。
- 配置缺省或为 0：采用默认 120 秒；负值配置被校验拒绝。
- 配置热更新：在途单笔请求按该笔开始时的配置快照执行，新发起的单笔请求按新值。
- r 透传路径与 a/c 路径一视同仁，同样受单笔总时长约束。
- 多个并发请求、多个源各自独立计时，超时互不影响。
- 多源场景的整轮时长可能随源数与每源耗时累加（每笔最多配置值），本次不做整轮
  上限（用户明确选择）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供单请求最大超时时长配置项，含全局默认值与可选的
  每源覆盖值；全局缺省或为 0 时 MUST 采用默认值 120 秒，任何位置的负值 MUST
  被配置校验拒绝。
- **FR-001a**: 某源未配置覆盖值时 MUST 继承全局值；配置覆盖值时 MUST 以覆盖值
  作为该源单笔请求的计时上限。
- **FR-002**: 该时长 MUST 按单个源的单笔请求计算（从该笔上游调用开始到结束），
  每笔尝试独立计时，MUST NOT 作为客户端请求整轮的累计上限。
- **FR-003**: 到点 MUST 取消该笔在途上游调用；该笔尚未产出内容时 MUST 按既有
  失败逻辑计入熔断统计，并允许按既有顺序继续尝试其他源或整轮重试。
- **FR-004**: 该笔未产出内容且最终整轮失败时，客户端 MUST 收到合法错误终态，
  MUST NOT 静默断流或无限挂起。
- **FR-005**: 到点前已向客户端写出事件时，源 MUST 保持锁定，请求 MUST 保留已
  收内容并以 failed 错误终态收口流，客户端 MUST NOT 再收到后续事件，且 MUST
  NOT 换源。
- **FR-006**: 单笔源请求超时导致的结束 MUST 与客户端取消可区分：终态、日志与
  指标 MUST 标记为超时原因；客户端取消 MUST NOT 被记录为超时，超时 MUST NOT
  被记录为 canceled。
- **FR-007**: 既有首字节超时的源级失败切换语义 MUST 保持不变：首字节超时约束
  "等待首个事件"并在该源失败时触发切换；单笔总时长约束"该笔请求全程"并走
  相同的失败路径；两个机制按先到者先生效。
- **FR-008**: 配置热更新或环境变量覆盖后，新发起的单笔请求 MUST 立即按新值
  执行，无需重启；配置示例、配置校验与回归测试 MUST 同步更新。

### Key Entities

- **单请求最大超时时长配置项**: 时长单位；决定单个源单笔请求的生命周期上限，
  含全局默认值（120 秒）与每源可选覆盖值。
- **单笔源请求**: 一次客户端请求为换取上游结果而发起的单次源调用，从该调用
  开始到其结束。
- **收尾终态**: 请求结束前客户端收到的最后一个事件；失败时为错误终态。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 未配置时每笔源请求默认按 120 秒执行；任何配置值下，单笔源请求
  从开始到结束的实际时长不超过配置值加收尾余量（1 秒量级），不再出现长达 360
  秒的单源无数据挂起。
- **SC-002**: 全部源若均超时或失败，客户端 100% 收到合法终态事件，静默断流或
  无限挂起为 0。
- **SC-003**: 同一操作场景下，单笔源请求超时结束与客户端取消结束在终态、日志
  与指标中可明确区分。
- **SC-004**: 已出流的单笔请求到点后同样收到 failed 收尾终态；配置值调整后
  行为边界随新值平移，回归测试通过。
- **SC-005**: 全量门禁（格式、静态检查、全部测试、race）通过；默认值、校验、
  环境覆盖与热重载行为有对应测试锁定。
- **SC-006**: 全局值、每源覆盖值与继承关系均被测试覆盖：覆盖源按覆盖值、
  未覆盖源按全局值执行，行为边界无串扰。

## Assumptions

- 超时支持全局默认 + 可选每源覆盖（沿用 `first_byte_timeout` 的覆盖模式）；v1
  不引入其他细粒度控制。
- 单笔总时长是单源请求的硬上限，覆盖已出流场景；它与"首字节超时只约束开始
  出流、不误判长思考或长输出"的既有语义不同，属于新增的单笔兜底机制，交付时
  必须同步更新相关文档或协议矩阵说明，避免被误读为既有首字节超时行为。
- 整轮时长不设上限，可能随源数与每笔耗时累加；这是用户本轮明确的选择（"不是
  要整轮"），如需整轮上限可后续扩展。
- 在途单笔请求使用该笔开始时的配置快照，配置热更新只影响新发起的单笔请求。
- 超时归因属于网关侧终止，不改变上游侧既有成功/失败状态记录语义，仅按既有
  失败逻辑计入熔断统计。
- 退避等待与整轮重试的等待间隙不属于任何单笔源请求，不受该配置直接约束。
